# Working on MixIt

## Commands

```sh
cargo fmt --all
cargo clippy --all-targets -- -D warnings      # default members (everything but the desktop app)
cargo test                                     # default members
MIXIT_SOAK_MINUTES=30 cargo test -p mixit-engine --test soak -- --nocapture   # long random session over every control (cargo test runs 1 minute; MIXIT_SOAK_SEED replays another, MIXIT_SOAK_TRACE prints each step)
MIXIT_HTDEMUCS_MODEL=/path/to/htdemucs_fp16weights.onnx cargo test -p mixit-ml --release --test htdemucs -- --nocapture   # the trained stem splitter on a generated track (skipped without the model file)
MIXIT_SPEECH=/path/to/speech.wav cargo test -p mixit-ml --release --test voice -- --nocapture   # the mic cleaner against a real voice recording instead of the generated one
MIXIT_CLAP_DIR=/path/to/models cargo test -p mixit-ml --release --test clap -- --nocapture   # the sound listener (CLAP) on generated tracks (skipped without the three model files)
MIXIT_MEL_ROFORMER_MODEL=/path/to/mel_roformer_kj_fp16.onnx cargo test -p mixit-ml --release --test mel_roformer -- --nocapture   # cleaner vocals (Mel-Band RoFormer) on a generated singer, next to HTDemucs's vocals when MIXIT_HTDEMUCS_MODEL is set too (skipped without the model file)
MIXIT_BEAT_THIS_MODEL=/path/to/beat_this_final0.onnx cargo test -p mixit-ml --release --test beat_this -- --nocapture   # the beat helper (Beat This!) on generated tracks, beats and grids against the truth (skipped without the model file)
MIXIT_BASIC_PITCH_MODEL=/path/to/basic_pitch_nmp.onnx cargo test -p mixit-ml --release --test basic_pitch -- --nocapture   # sound to notes (Basic Pitch) on generated melodies and chords (skipped without the model file)
MIXIT_UPDATE_REGISTRY=1 cargo test -p mixit-core --test registry_snapshot   # after changing the action registry: rewrites the copy the UI tests (Ask MixIt) check against
cargo clippy -p mixit-desktop --all-targets -- -D warnings   # needs the webview toolchain
cargo build --target wasm32-unknown-unknown -p mixit-core -p mixit-dsp -p mixit-engine -p mixit-analysis -p mixit-generator -p mixit-project
cargo build --target wasm32-unknown-unknown -p mixit-stretch --no-default-features

cd apps/desktop
npm run typecheck && npm test && npm run build
npm run wasm         # builds the engine for the browser into public/mixit.wasm
node scripts/wasm-smoke.mjs   # checks that module: no imports, generate, analyse, play
npm run e2e          # end-to-end browser test of the main flows on the demo backend (needs Playwright + Chromium)
npm run dev          # UI in a browser: the real engine if public/mixit.wasm exists, else the demo (?demo forces it)
npm run tauri dev    # the real app
```

On small machines build the desktop crate with `-j 2`; linking it with full parallelism can run out of memory.

## Architecture

- **The audio thread never allocates, locks or blocks.** The UI talks to the engine through `Controller` (a lock-free command ring); the engine reports back through `Telemetry` (a copyable snapshot) and an event ring. Anything that allocates (stretchers, decoded tracks, grids) is built off the audio thread and sent in; old objects go back through the trash ring to be dropped elsewhere.
- **One action registry** (`mixit-core::actions`) names every control (`deck.A.play`, `mixer.B.eq.low`, `fx.A.1.mix`). Keyboard shortcuts, the command palette, explain mode, tooltips and (later) MIDI mapping all come from it. `mixit-engine::actions::ActionDispatcher` turns an action and input into engine commands; `app.*` actions and a few deck actions (`key_sync`, `grid.*`) are handled by the app.
- **Per-system differences live in one table each:** `mixit-host::platform` (folders, default audio buffer, names the system uses) and `src/lib/platform.ts` (shortcut labels, file names from either kind of path). Each rule is a function of the system, so tests check Windows, macOS and Linux on any machine. Add new per-system behaviour there instead of testing the system elsewhere, and name files with `mixit_library::m3u::safe_file_name`.
- **Trained models** live in `mixit-ml` (native only): `models::ModelStore` downloads each model file once into the models folder beside the library and checks its SHA-256; `stems` runs HTDemucs through ONNX Runtime (`ort`) in overlapping 7.8 s pieces. With setting `cleanVocals` (off by default: several minutes a track), `vocal_split` runs Kim's Mel-Band RoFormer after it (STFT and inverse done here, 8 s pieces every 4 s as the authors' `demix()`), and its vocals replace HTDemucs's (stem method `htdemucs+mel-roformer`, falling back to HTDemucs's vocals). `sound` runs CLAP for search by sound: `log_mel` reproduces CLAP's own feature extractor exactly, each track is heard in up to four 10 s windows after analysis (desktop `listen.rs`), and the library keeps the numbers per model in `sound_embeddings` (`sounds_like` weighs them with the analysis's timbre profile; `sounds_described` ranks tracks against a description). `beats` runs Beat This! (log-mel front end reproduced exactly, 30 s pieces with the authors' borders and peak picking); after analysis, tracks whose grid confidence is below 0.6 get its second opinion (desktop `beats.rs`), `mixit-analysis::heard` turns its beats into a grid and names how it differs, and the library keeps it in `grid_suggestions` for the deck to offer (Use it / Keep this one), never applied on its own. `notes` runs Basic Pitch (230 KB; 2 s windows overlapping by 30 frames, each kept frame at its exact time) and turns what it hears into notes with our own rules (onset peaks or strong soft starts, overtones of a clearer note below dropped); desktop `notes.rs` (`pad_notes`) hears a pad's sound and the sequencer's "Turn a pad's notes into a pattern" lays them on squares (`notesToPattern`), each pitched by `SamplerCommand::SeqPitches` (semitones per step, sent in rows of 16). `voice` cleans the mic: WebRTC's echo canceller (`sonora`, pure Rust, tuned to keep the voice whole over music) then DeepFilterNet3 (built in, run with `tract`) or RNNoise; `mixit-host::voice` runs it on its own thread between the input callback and the engine, which sends the music (master without the mic) back through `InputFeed::echo_tap`. Every helper is optional: behind a cargo feature (`stems-model`, `mic-clean`, `sound-search`, `beat-helper` and `sound-to-notes` in the desktop app, `onnx`, `voice` and `sound` in `mixit-ml`, `voice-clean` in `mixit-host`) and a setting, and the code that uses it falls back to what worked before (the quick split) when the model is missing or fails (the raw mic, for the cleaner; the analysis's own profile, for "sounds like").
- **Finish my mix** (`mixit-analysis::finish`, no model, wasm-safe): the report after a recording offers a finished copy, "<name> (finished).wav" beside it (desktop `finish_mix`, a "finish" job). It compares the mix's balance in ten octave bands (louder half of the music) with a track the mix played, or smooths the mix's own bumps for club (-9 LUFS) or streaming (-14 LUFS) level, turns the difference into gentle EQ (at most 6 dB, 3 when smoothing), then sets the loudness under a -1 dBTP limiter and says what it changed in plain words. The recording itself is never changed.
- **wasm-safe crates** (core, dsp, engine, analysis, generator, project, web, and stretch without its default `signalsmith` feature) must not use threads, files or system audio. Native-only code lives in io, library, host, cli and the desktop app.
- **Desktop app:** `src-tauri/src/commands.rs` exposes the backend; `telemetry.rs` streams engine state to the UI at display rate and writes recordings; DTOs in `dto.rs` are camelCase and mirrored in `src/backend/types.ts`.
- **UI:** every call goes through the `Backend` interface (`src/backend/index.ts`). In a plain browser the `DemoBackend` simulates the engine and library, so UI work and screenshots need no Rust build. Keep it in step when you add a command.
- **Arrange rendering:** `mixit-engine::arrangement::ProjectRenderer` plays a `MixProject` through the engine offline, a piece at a time, asking for each track just before its clip starts. Natively `mixit-host::project` wraps it with Signalsmith; in the browser `mixit-web::render` drives it from the worker with the phase vocoder, for Arrange preview and render.
- **Browser engine:** `crates/mixit-web` wraps the engine, dispatcher, generator and analysis behind a plain C ABI (no wasm-bindgen: the module must have no imports so an AudioWorklet can instantiate it). `public/mixit-worklet.js` renders it, `public/mixit-worker.js` generates and analyses, `src/web/engine.ts` is the page side and `src/backend/web.ts` (`WebAudioBackend`, extending the demo for library features) routes decks, mixer, sampler and recording to it. Key lock there uses `mixit_stretch::PhaseVocoder` (Signalsmith needs C++).
- **UI state:** zustand stores. Canvas loops (waveforms, meters) read `useTelemetry.getState()` every frame instead of re-rendering React. Selectors must return primitives or stable references (zustand 5 re-renders forever on a new array each time).
- **Mix screen and windows:** the waveforms, decks, mixer and library stay fixed; sampler, sequencer, effects, mic and recording share the tools panel (`components/shell/ToolPanel.tsx`). The library and tools panel can open on other screens (`src/lib/screens.ts`, Rust `windows.rs`): a part window is the same UI with `?part=`, and `src/lib/windowSync.ts` keeps UI-only values (mixer, pads, sequencer, mic) in step between windows. Only the main window pushes engine state and records.
- **Ask MixIt** (`src/lib/ask.ts`): the command palette also reads a request typed in plain words ("cut the bass on deck B", "find instrumentals around 124 bpm", "build a one hour warm-up set") and turns it into registry actions, a library search, search by sound, Play next or Build a set's settings. Phrase rules, no language model; `understand` only reads, `askRun.ts` acts. Add a sentence to the test set in `src/test/ask.test.ts` with every new rule (it must stay at 95 % or more), and keep the tests' registry copy current (the `registry_snapshot` test fails until you do). Setting `ask` turns it off.
- **Updating while we test** (`src-tauri/src/update.rs`, `src/lib/update.ts`, Settings > About): the app is built from a git checkout on the same computer (`build.rs` stamps the commit and folder in). Update fetches that checkout, pulls with `--ff-only` (never over unsaved changes), runs `npm run tauri build` through the login shell so Node and Rust are found, and swaps the new `.app` in (macOS so far; the per-system parts are in `mixit-host::platform`). No GitHub builds and no tags: version tags only when Nachi asks with the word "doitbaka".
- **Controls** go through `act`/`press`/`setValue` in `src/lib/actions.ts`, which also mirror mixer and FX values into the store (the engine does not report them back).

## Conventions

- Tests generate their audio with `mixit-generator`, so every claim (BPM, key, beat positions, section boundaries) is checked against exact ground truth.
- User-facing text is plain language for someone who has never DJed: say what a control does, not its jargon.
- Easy view shows the essentials; Pro shows everything. Never lock a feature behind Pro, only hide it.
- Commit messages: imperative subject, a body that says what and why.
